# Webhooks product guide

## What are webhooks

A webhook is an HTTP callback: a request that [[= product_name =]] sends to an external URL when something happens in the repository.
Instead of polling the REST API to find out whether content has changed, external systems, such as a CRM, a search index, a static site generator, a CDN, or an automation platform, receive a notification the moment a change happens.

Each notification is a small JSON document that describes the event, the user who triggered it, and the identifiers of the affected content.
The receiving system can then fetch any additional data it needs through the [REST API](rest_api_usage.md), using the links included in the notification.

## Availability

Webhooks are available in all [[= product_name =]] editions.
The feature is delivered as the `ibexa/webhooks` package and requires [installation and configuration](configure_webhooks.md) before you can use it.

## How do webhooks work

### Webhook

A webhook is a subscription that consists of:

- a name, which helps administrators recognize the webhook
- a payload URL, an absolute `http://` or `https://` address of the receiving endpoint
- one or more event types that the webhook subscribes to
- optional filters that narrow down the events
- a signing secret, generated by the system, used to sign every request
- a status: enabled or disabled

The user who creates the webhook becomes its owner and receives a notification if the webhook is disabled automatically.

You can manage webhooks [in the back office]([[= user_doc =]]/webhooks/work_with_webhooks/), through the [REST API](webhooks_api.md#rest-api), or with the [PHP API](webhooks_api.md#php-api).
Access to all these operations is controlled by the [`webhook` policies](permissions/policies.md#webhooks).

### Event types

Out of the box, webhooks can subscribe to 21 repository events, grouped as follows:

| Group | Event types |
|---|---|
| Content | `content.published`, `content.created`, `content.deleted`, `content.hidden`, `content.revealed`, `content.copied`, `content.metadata_updated` |
| Trash | `trash.trashed`, `trash.recovered`, `trash.emptied` |
| Location | `location.created`, `location.moved`, `location.deleted`, `location.hidden`, `location.unhidden`, `location.swapped` |
| User | `user.created`, `user.updated`, `user.deleted` |
| Section | `section.assigned` |
| Object state | `object_state.set` |

For a description of each event and the data it carries, see [Webhook payload reference](webhook_payload_reference.md#event-types).

Developers can add their own event types, for example, to react to events coming from custom code.
For more information, see [Extend webhooks](extend_webhooks.md).

### Filters

By default, a webhook receives every occurrence of the events it subscribes to.
You can narrow this down with the following filters:

- **Content types** - only events that concern content of the selected content types
- **Sections** - only events that concern content assigned to the selected sections
- **Subtrees** - only events that concern content located in the selected subtrees

All filters that you set must match for an event to be delivered.
Within a single filter, matching any of the selected values is enough.
An empty filter matches all events.

For example, a webhook with the "Article" and "Blog post" content types and the "Media" subtree selected receives events only for articles and blog posts that are located under "Media".

!!! note "Events without content context"

    The `location.swapped` and `trash.emptied` events don't concern a single content item, so filters can't be evaluated against them.
    A webhook subscribed to one of these events receives every occurrence, regardless of its filters.

### Delivery

When a subscribed event occurs, [[= product_name =]] creates a delivery: it builds the JSON payload, stores it in the delivery log, and places it in a dedicated message queue.
A background worker picks up the delivery and sends it to the payload URL.

Every request is signed with an HMAC signature computed from the webhook's signing secret, so that the receiver can verify that the request comes from [[= product_name =]] and wasn't modified on the way.
A timestamp header allows the receiver to reject replayed requests.
For more information, see [Webhook payload reference](webhook_payload_reference.md#signature-verification).

A delivery succeeds when the receiver responds with any `2xx` HTTP status code within the configured timeout.
A failed delivery is retried automatically, with an increasing delay between attempts.

Capturing events never interferes with editorial work: if anything goes wrong while matching webhooks or queuing deliveries, the error is logged and the original repository operation completes normally.

### Delivery log

Every delivery is recorded together with its status, number of attempts, HTTP response code, duration, error message, and the exact payload that was sent.
A delivery can have one of the following statuses:

| Status | Description |
|---|---|
| Pending | The delivery is queued and waits for the worker. |
| Success | The receiver responded with a `2xx` status code. |
| Failed | The last attempt failed. If retries remain, the delivery is attempted again. |
| Skipped | The webhook was disabled before the delivery was sent. |

From the delivery log, administrators can view the payload of each delivery and re-send it, for example, after an outage of the receiving system has been fixed.
They can also send a test delivery to check whether the receiving endpoint is reachable and verifies signatures correctly.

Delivery log entries are removed automatically after a configurable [retention period](configure_webhooks.md#delivery-log-retention).

### Automatic disabling

If deliveries to a webhook keep failing, for example, because the receiving system has been decommissioned, the webhook is disabled automatically after a configurable number of consecutive failures.
The owner of the webhook receives a back office [notification](notifications.md) with a link to the webhook.

A successful delivery resets the failure counter.
Once the problem is fixed, an administrator can enable the webhook again.

## Capabilities

### Management in the back office

Administrators can create, edit, enable, disable, test, and remove webhooks in the **Admin** section of the back office, and browse the delivery log of each webhook.

### REST API

All management operations, including the delivery log, test deliveries, and re-sending, are available in the REST API, which makes it possible to automate the setup of integrations, for example, as part of a deployment.

### Secure by default

Signing secrets are generated by the system, encrypted at rest, and displayed only once, right after they are created or regenerated.
Every request carries an HMAC signature and a timestamp.

### Extensibility

Developers can add new event types with a single service definition, and control the data included in the payload by providing their own extractors.

## Benefits

### Real-time integrations

External systems learn about changes the moment they happen, instead of polling the repository on a schedule.
Search indexes, caches, and downstream channels stay up-to-date without delay.

### Less custom code

Integrations that would otherwise require custom event subscribers and HTTP clients can be configured in the back office by an administrator, without a deployment.

### Reliability

Asynchronous delivery, automatic retries, and a complete delivery log with re-sending make sure that no change is lost when the receiving system is temporarily unavailable.

### Transparency

The delivery log shows exactly what was sent, when, and with what result, which makes troubleshooting integrations fast and straightforward.
